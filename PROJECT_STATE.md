## 1. Продукт и текущая зрелость

Цель продукта: выбор топлива → подсказки безопасных режимов поездки → read-only сбор диагностических данных BMW через ENET/VXSCAN → сравнение сигналов и оценка достаточности данных → заключение с ограничениями.

**Реально реализовано:** дорожные наблюдения и измерения, исследовательская карта покрытия, отдельный тест заправки с предварительным **относительным** сравнением детонационных сигналов. **Не реализовано/не подтверждено:** независимая лабораторно привязанная классификация топлива, определение истинного RON/MON и универсальная точность для иных автомобилей/прошивок/составов топлива.

## 3. Схема компонентов и данные

```text
MainActivity / OctaneDashboard
          ↑ статусы, прогресс и диагностические события
          |
EnetLoggerService (foreground; один рабочий TCP reader / polling loop)
     ├─ AndroidNetworkEventMonitor + discovery (Ethernet / Wi-Fi VXSCAN)
     ├─ HsfzCodec + DiagnosticResponse / DmeBatchParser / MixedDidBatch
     ├─ PollModePolicy (B+ default → B → A), SlowPollScheduler, SampleFreshness
     ├─ DmeMonitorPolicy (низкий приоритет; тот же TCP-сеанс)
     ├─ FuelRefillDetector и существующий Fuel Score / OctaneCalibration
     ├─ BaselineLearning / SteadyCellStats (исследовательские данные)
     ├─ GuidedFuelTest (независимый тест заправки)
     └─ SteadyTargets (покрытие 2 конкретных STEADY-регионов)
DmeHistoryReader / DmeHistoryProtocol
  └─ отдельный one-shot TCP только при остановленном LOGGER
```

- ENET/HSFZ: UDP discovery 6811; диагностический TCP 6801. Прикладные сообщения имеют явное фреймирование; UDS ответы валидируются по SID/DID и длине.
- Доступны интерфейсы Ethernet/USB ENET и Wi-Fi/VXSCAN; фактическая маршрутизация Android зависит от устройства/прошивки. `AndroidNetworkEventMonitor` наблюдает сети и не переключает самостоятельно системную мобильную маршрутизацию.
- B+ — read-only смешанный пакет 4 knock DID по 4 байта и 4 ignition DID по 2 байта. Режимы C/D и одновременное второе TCP-чтение удалены; прежнее авто-сравнение A/B также удалено.
- `measurement_mode=AUTO` — алгоритм захвата режимов движения и **не** режим автоматического выбора протокольного polling.
- DME Monitor пытается читать только допустимые низкоприоритетные значения **после** завершённого FAST; ошибки протокола не должны быть приняты как текущая FAST-телеметрия. Полный DME history scan работает лишь с отключённым LOGGER.
- Данные и пользовательские настройки остаются локальными: SharedPreferences `bmw_native`, файловый каталог приложения (обычно `getExternalFilesDir(null)`, иногда `filesDir`).

## 4. Алгоритмы топливных исследований

### Legacy Fuel Score и калибровка

`OctaneCalibration.kt` содержит замороженные архивные референсы: ACCEL для RPM 2500–4499 при MAP ≥200 кПа, исторический STEADY — только RPM 1300–2399, MAP 88–104 кПа, LOAD 15–68%. Для незнакомых STEADY-областей функция `steadyReference` **возвращает null**, не экстраполирует значения. Внутренний score и метки `NORMAL/BORDERLINE/BELOW BASELINE` в `EnetLoggerService.kt` — **относительные программные индикаторы**, не измеренное октановое число и не итоговая независимая оценка соответствия топливу.

### BaselineLearning — исследовательская карта

`BaselineLearning.kt` ведёт отдельные карты RPM × LOAD для STEADY и ACCEL и хранит данные в `bmw_baseline_learning_v1730_<id>.csv`. Наблюдательная ячейка может достичь **ready for review** при ≥24 точках, ≥4 сегментах, ≥2 запусках LOGGER. Это не подтверждение марки бензина. Кандидатный CSV не подключается к рабочей `OctaneCalibration`, наборы неизвестного топлива не повышаются автоматически до эталона.

### GuidedFuelTest — независимая заправка

`GuidedFuelTest.kt`, `MainActivity.kt`, `EnetLoggerService.kt`:
- **НОВАЯ ЗАПРАВКА** (только при остановленном LOGGER): выбрать заявленный АИ, необязательное название АЗС; приложение запускает LOGGER с `measurement_mode=AUTO`. Оценка открывается в **диалоге** по кнопке новой заправки, а не занимает постоянный блок главного экрана.
- `bmw_fuel_test_v1731_<id>.csv` отделён от исследовательской базы. Важны физические условия, качество датчиков, топливная сессия и повторные сегменты.
- «Предварительный сбор завершён»: ≥2 STEADY RPM×LOAD-ячейки и ≥3 ACCEL RPM-группы, каждая ≥4 принятых точки из ≥2 сегментов. Достаточность данных для предварительного сравнения **не** доказывает хорошее/плохое топливо.
- Относительное изменение детонационного сигнала рассчитывается по сегментам и сравнимым архивным RPM-группам (≥2 с референсами); сертифицированного RON не получается.

### SteadyTargets v1.7.32 — две недостающие области

`SteadyTargets.kt` и `EnetLoggerService.kt`:
- 2500–2999 и 3000–3499 об/мин **при абсолютном MAP [105,130) кПа**, отдельно.
- Из обычного `AUTO` LOGGER, без специального обучения нового топлива и **без дополнительных ECU-запросов**.
- Принятие с прогретым двигателем, валидными knock/ignition каналами, стабильным STEADY, сопоставимыми trims, известной скоростью, без активных детонационных событий и без процесса перемешивания.
- Удержание режима ≥5 секунд, пауза между принятыми точками ≥2,5 секунды; новая серия при смене целевого диапазона или разрыве >6 с.
- Предварительное покрытие **каждого** диапазона: ≥24 точек, ≥4 независимых сегментов внутри запусков и ≥2 разных запусков LOGGER. Запуски не равны независимым заправкам/дням.
- Прогресс сохраняется в `bmw_steady_targets_v1732_fuel<id>.csv`, восстанавливается по той же сессии топлива и **не объединяется** с чужой заправкой. Не влияет на рабочую калибровку.

## 6. Открытые ограничения и следующие приоритеты

**Не проверено этой документационной итерацией:**
1. Привязка относительных knock-сигналов к независимо проверенной марке и RON; нужны известные лабораторные/достоверно подтверждённые топлива, контроль конфаундеров и hold-out по **целым поездкам/заправкам**.
2. Достаточность и повторяемость в недостающих STEADY-областях при реальном движении; пользовательские значения нельзя интерпретировать как статистически независимые без анализа сегментов.
3. Живые тайминги, потери пакетов, reconnect и совместимость с конкретным VXSCAN/Android, в том числе одновременный мобильный интернет при подключённом Wi-Fi адаптере.
4. Полнота данных DME/адаптаций для конкретной прошивки: неподдерживаемые DID и NRC нельзя трактовать как нули.
5. Новые аппаратные испытания или новая сборка в рамках **только документационного** PR.

**Приоритеты дальнейшей работы:** качество и независимость телеметрии → воспроизводимые безопасные дорожные серии → валидация относительных моделей → улучшения интерфейса, не создающие дополнительные небезопасные сетевые операции.
