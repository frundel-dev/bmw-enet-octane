# AGENTS.md — правила совместной разработки BMW OCTANE

Действует для всего репозитория. Это руководство для разработчиков и AI-агентов; не заменяет техническую проверку, требования безопасности или разрешения на изменения.

## 1. Назначение продукта

BMW OCTANE — Android/Kotlin-приложение для **исследовательского сравнения качества топлива** по read-only диагностическим данным BMW через ENET/VXSCAN.

Основной сценарий: **выбор заправленного топлива → безопасные подсказки по режимам движения → сбор телеметрии → оценка полноты выборки → обоснованное относительное сравнение с достоверностью и ограничениями**. Текущая версия **не** измеряет лабораторное октановое число RON/MON, не сертифицирует марку топлива и не должна выдавать экспериментальную корреляцию за измерение.

Приоритет: безопасность и целостность данных → корректность измерений и интерпретации → отсутствие регрессий → продуктовая цель → сопровождаемость/тестируемость → производительность/UX → скорость добавления функций.

## 2. Режимы работы

- **ОБСУЖДАЕМ:** анализ цели, альтернатив, рисков и зависимостей; код не изменять.
- **РЕАЛИЗУЙ:** изучить актуальную ветку и затрагиваемые компоненты, выбрать минимальное надёжное решение, внести изменения, выполнить доступные проверки и сообщить об ограничениях.
- **ПРОВЕРЬ:** аудит поведения/кода/тестов/логов; не добавлять новые функции без необходимости.
- **ОТКАТИ:** восстановить конкретный проверенный коммит/изменение с минимальным побочным эффектом; не уничтожать чужие изменения.

Если режим не задан, определять по смыслу запроса. Не изменять репозиторий при запросе на обсуждение.

## 3. Перед реализацией

1. Кратко переформулировать цель задачи и критерии готовности; для ясных задач не запрашивать лишнее согласование.
2. Получить **текущее** состояние GitHub (ветка, коммит, файлы), а не принимать воспоминания или старые архивы за источник истины.
3. Проследить вызовы и зависимости: UI ↔ Service ↔ network/protocol ↔ collection/CSV ↔ model ↔ tests.
4. Выявить скрытые риски (перемешивание топлива, недостоверные данные, параллельный сокет, невалидная телеметрия, изменение форматов).
5. Критически оценить предложенную реализацию; если есть безопаснее/проще — объяснить и выбрать обоснованный вариант.

Если актуальный код или необходимые инструменты недоступны, назвать это ограничение, не выдумывая проверки.

## 4. Неприкосновенные диагностические инварианты

- Диагностические запросы к ECU — **только чтение**, пока отдельная явно согласованная функция не потребует иного; никакого coding/flashing/reset/clear DTC/security-access/write/routine/IO-control по умолчанию.
- Для TCP/HSFZ проверять целые фреймы, длины, типы, заголовки и ограничения размера. TCP read не равен границе сообщения.
- Для UDS контролировать SID/NRC, DID, порядок, длины, соответствие ответов запросам; не подменять данные одного цилиндра данными другого.
- Не вводить конкурентное чтение одного TCP-сокета. FAST, SLOW и DME Monitor должны оставаться сериализованными, а отдельно читаемая история DME не должна открываться одновременно с активным LOGGER.
- Обрабатывать timeouts, прерванные ответы, late responses, отмену, переподключение и безопасный fallback B+ → B → A там, где это определено кодом.
- Не ухудшать достоверность диагностики ради частоты обновления UI: исследовательские панели должны по возможности потреблять существующие валидированные FAST/SLOW данные без новых опросов.
- Учитывать lifecycle foreground Android Service, права доступа к сети, сетевые binding/маршруты и Android Wi-Fi/mobile data ограничения.
- При проблемах записи CSV нельзя сообщать о накоплении данных, которых не удалось сохранить.

## 5. Требования к научной корректности

- Различать **качество и полноту измерений**, **относительные сигнальные отличия** и **валидированное качество топлива**.
- Не обучать текущую топливную модель на бензине с неподтверждённой маркой и не назначать неизвестное топливо эталоном самому себе.
- Не менять без отдельной проверки замороженный `OctaneCalibration.kt`; любое изменение модели требует обоснования, фиксированных датасетов и независимых hold-out тестов.
- Сохранять сегментацию по поездкам/запускам LOGGER и сессиям топлива. Соседние записи высокочастотного опроса не являются независимыми поездками.
- Не объединять автоматически данные разных заправок, наборов обучения, несовместимых версий CSV и неподтверждённых состояний перемешивания.
- Явно описывать влияние IAT, температуры охлаждающей жидкости, нагрузки/MAP, коррекций смеси, адаптаций DME и особенностей прошивки.
- Процент покрытия, confidence и legacy Fuel Score не эквивалентны оценке истинного RON.

## 6. Надёжность изменений

- Небольшая задача — отдельная короткоживущая feature/fix/docs ветка и PR в `main`.
- Сохранять публичные интерфейсы и форматы файлов, если их изменение не согласовано и не обеспечено миграцией.
- Добавлять соответствующие JUnit/регрессионные тесты, особенно на framing, ошибки UDS, граничные условия, жизненный цикл, топливные сессии и повторяемость.
- Для кода проверять минимум `:app:testDebugUnitTest`, `:app:lintDebug`, `:app:assembleDebug` при наличии среды; при отсутствии — использовать доступные CI, явно сообщать результаты.
- Реальные поездки и лабораторную валидацию не считать выполненными по причине успешной сборки.
- Самостоятельно выполнять доступную инженерную работу, не перекладывая чтение исходников/копирование кода на пользователя. Разрушительные/необратимые действия требуют разрешения.

## 7. Факты, гипотезы и отчёт

В каждом техническом заключении отличать:
- **Проверено:** конкретная версия файла, коммит, тест или лог с наблюдаемым результатом.
- **Предположение:** объяснение с оговоркой, что оно не подтверждено.
- **Не проверено:** аппаратные, дорожные и статистические вопросы, для которых не было проверки.

После реализации сообщать кратко:
- **Что сделано; почему; исходный SHA и итоговый SHA/PR.**
- **Что проверено:** названия команд/CI, реальные статусы.
- **Что не проверено:** конкретные ограничения.
- **Что проверить на автомобиле:** исключительно то, что действительно требует оборудования.
- **Как воспроизвести и откатить** изменения.

Не утверждать успех тестов, сборки или дорожных измерений без фактического результата.

## 8. Документация и порядок работы между чатами

- `README.md`: входная точка и инструкция по актуальному приложению.
- `PROJECT_STATE.md`: доказанный срез `main`, версии, ограничения и открытые вопросы.
- `DECISIONS.md`: принятые в коде решения и их мотивация; новые гипотезы отдельно от действующих решений.
- `docs/*_v*.md`: исторические, версионные исследования и проверки; не переписывать старую историю под нынешний UI.

Ссылки на источник истины — файлы и коммиты GitHub, а не память отдельного чата. При смене версии документация должна обновляться вместе с реализацией. Если документация противоречит коду, сначала установить факт по актуальному коду, затем исправить документацию, не скрывая ограничений.

**Итоговый принцип:** меньше неоправданной сложности, больше проверяемости и воспроизводимой диагностической информации.
