# BMW OCTANE 2.0.1 LAB (versionCode 202) — исправленная логика первой заправки

**Ветка:** `feature/octane2-refuel-confirmation` (PR #23). Изменения из PR #25 перенесены в 2.0.1; `versionName` остаётся 2.0.1, а `versionCode=202` обеспечивает обновление поверх ранее установленной 2.0.1 (код 201). `main` не меняется. Предыдущее поведение сохранено для всех **уже подтверждённых** сессий.

## Проблема, подтверждённая кодом до изменения

При новой установке кнопка START запускала `EnetLoggerService` без `guided_fuel_test_id` и марки бензина. Когда пользователь позднее выбирал топливо в ручной форме, `RefuelSessionStore.confirm()` **всегда** делал `fuel_session_id + 1` и назначал `MIXING=5 км`, ошибочно представляя изначальное топливо как новую заправку.

## Проверяемое решение

1. Главная кнопка `НАЧАТЬ СБОР`: если `RefuelSessionStore.hasCurrentFuel()==false`, показывает выбор марки; диагностический Service ещё **не запускается**. Только после удачного подтверждения начального выбора автоматически выполняется исходное нажатие START. Отмена не запускает сбор.
2. Начальный выбор АИ-95/АИ-98/АИ-100 создаёт подтверждённую исходную запись с самостоятельным ID теста и привязкой к **существующему** идентификатору `fuel_session_id`. На новой установке он равен **1**. `MIXING=0`, состояние `COLLECTING`, `PREF_LAST_SOURCE=INITIAL`. Ни временная метка, ни марка не используются как номер сессии. В уже существующей базе с `fuel_session_id > 1` существующая нумерация сохраняется, никаких CSV не перезаписывается и не перенумеровывается.
3. На последующих нажатиях START имеющееся подтверждённое топливо остаётся текущим, новая сессия не создаётся. При первой инициализации сбрасывается **только кэш последнего OBD PID 0x2F** из старой версии, чтобы детектор заново установил опорный уровень; исторические диагностические CSV не трогаются.
4. Подтверждение **реальной последующей заправки** — автоматической после стабильного OBD `01 2F` или ручной — как раньше создаёт `fuel_session_id+1`, `MIXING` и новую аналитическую запись с сохранением старых данных. `REFUEL_PENDING` не повышает ID.
5. Дополнительный отказоустойчивый барьер в `EnetLoggerService.onStartCommand`: даже прямой или `START_STICKY` запуск без исходного подтверждённого топлива немедленно прекращается. При отсутствии или рассогласовании метаданных в активном цикле блокируются capture, STEADY/ACCEL и относительное сравнение, но сырые журналы не подменяются.
6. Для нового выбора используется ограниченный список `GuidedFuelTest.selectableGrades` (АИ-95, АИ-98, АИ-100); полная историческая шкала `GuidedFuelTest.grades` (включая АИ-92 и «Другое») сохраняется для совместимости. При редактировании исторической АИ-92 исходный вариант доступен, чтобы сохранение без изменений не переименовало топливо.
7. Форма субъективной оценки остаётся в диалоге заправки; исходный выбор не создаёт новый baseline или лабораторный RON.

## Границы итерации

Не тронуты `HsfzCodec`, TCP-сокеты, ENET/VXSCAN, UDS, RAM, packet parser, `PollModePolicy`, Coroutine Channels, файловая архитектура и форматы старых CSV. Отдельное изменение топливных prefs сохраняет уже существующие измерения.

## Автоматические проверки

`RefuelSessionStoreTest` охватывает: первая установка → №1, нет MIXING; перезапуск → та же сессия; последующее подтверждение → №2 и MIXING; отказ и pending сохраняют прежнюю сессию; миграция со старым номером не перенумеровывает данные; АИ-92 читается из истории, не предлагается как новый бензин. `:app:testDebugUnitTest`, `:app:lintDebug`, `:app:assembleDebug` запускаются в GitHub Actions для PR.

**Нужна проверка на автомобиле:** первое подключение, восстановление после остановки LOGGER и Android Activity, обнаружение следующей реальной заправки по PID 0x2F, длительный переходный период, сохранение телеметрии и приоритетных STEADY-режимов. Сборка не подтверждает научную оценку топлива.
